# “小邮书”校内社交平台需求分析与需求文档草案

## 1.任务概述

### 1.1目标 

<p style="text-indent: 2em;">“小邮书”致力于建设一个面向北邮在校学生、兼具身份可信、使用便捷和内容可沉淀特征的校内社交平台。<p>

**背景与现状**  
<p style="text-indent: 2em;">目前校内信息交流渠道仍存在不足。<p>
<p style="text-indent: 2em;">当前北邮校内信息传播除了学校官方信息发布网站之外，主要依赖北邮人论坛（官方）与微信校园墙两类渠道：<p>
<p style="text-indent: 2em;">前者论坛板块分类较为复杂，需要提前观看北邮人论坛手册后使用，虽在求职升学、学习交流与高信息密度内容沉淀方面具有稳定价值，但整体易用性较低，并对新生覆盖与轻量化互动支持不足；后者主要依靠微信个人朋友圈发帖，存在审核链路长、发布滞后、检索能力弱、传播范围有限等问题。<p>
<p style="text-indent: 2em;">基于此，本项目拟构建“小邮书”项目，面向校内学生提供易用性较强、传播速度快、能够分类检索与持续访问的社交平台。<p>
<p style="text-indent: 2em;">“小邮书”相比以往渠道，更强调易用性高、即时表达、便捷检索与内容沉淀，提升校园信息传播的效率与可持续利用价值。<p>

### 1.2系统（或用户）的特点 

**系统特点**
| 分析角度   | 小邮书                            | 微信校园墙              | 北邮人论坛                    |
| ------ | ------------------------------ | ------------------ | ------------------------ |
| 信息响应效率  | 较高，适合即时性校园信息传播                 | 较低，发布受人工审核与排队影响明显  | 中等，更适合持续性讨论与经验分享         |
| 检索能力   | 支持关键词检索、分类筛选与模糊搜索              | 基本不具备有效搜索能力        | 支持关键词搜索，但检索灵活性和容错性有限     |
| 平台易用性   | 较高，界面直观，便于新用户快速使用              | 较高，但功能较为单一         | 相对较低，需要熟悉版面结构和发帖规范       |
| 内容形式   | 支持短文本、图文、问答、寻物、搭子、生活分享等多种内容形式，并支持分类、标签、搜索与推荐   | 以微信用户个人投稿内容为主，多为捞人、吐槽、寻找搭子、失物招领等         | 以主题帖、经验帖和讨论帖为主           |
| 审核机制   | 采用“Agent机器审核+人工审核”的二级审核模式      | 主要依赖人工审核           | 主要依托站规、版规及版主/站务人工巡查与事后处置 |
| 互动方式   | 支持点赞、评论、收藏、关注等多种互动方式           | 互动主要依托微信朋友圈，时效性不足 | 以回帖讨论为主，轻量化互动相对不足        |

**最终用户特点**
<p style="text-indent: 2em;">本软件的最终用户主要为北京邮电大学在校学生。总体来看，用户需求涵盖校园生活交流、活动获取、寻物寻人、搭子匹配、经验查询和学习就业信息获取等多个方面，具有较强的时效性需求与互动需求。<p>

**预期使用频度**
<p style="text-indent: 2em;">结合现有校园信息传播渠道的使用特点，本软件预期属于中高频使用的校园信息服务平台。<p>
<p style="text-indent: 2em;">普通用户的主要使用方式为日常浏览、按需互动和场景化发布，预计整体使用频率为每周多次，其中部分活跃用户可达到每日使用。对于新生用户、活跃发布用户及具有即时信息需求的用户，在开学季、考试周、选课期和校园活动集中期等场景下，使用频率预计将进一步提升。<p>

### 1.3假定和约束

**假定**

1.假定本系统的目标用户均为北京邮电大学在校学生，并具备基本的网页端或移动端使用能力。

2.假定学校网络环境能够支持本系统的正常访问与使用。

3.假定项目开发期间所需的软硬件资源能够按计划提供。

4.假定本系统所依赖的身份认证、账号管理及相关数据来源能够正常接入。

5.假定项目成员能够在约定开发周期内按照既定分工完成需求分析、系统设计、编码实现与测试等工作。

**约束**

1.本项目开发周期约为三个月，需在限定时间内完成系统设计、实现与测试工作。

2.系统开发需以大模型模糊搜索模块和AI审核模块为重点。

3.AI审核功能需与人工审核机制配合，实现内容审核的效率与准确性平衡。

4.项目经费、服务器资源和测试条件有限，技术方案应满足低成本、可部署要求。

5.系统开发与运行需符合校园管理要求及相关法律法规。

## 2.需求规定

### 2.1软件功能说明 

<p style="text-indent: 2em;">本系统面向北京邮电大学在校学生，主要提供账号认证、内容发布与浏览、互动交流、智能检索及内容审核等功能。其中，系统开发重点为基于大模型的模糊搜索模块与AI审核模块，以提升校园信息获取效率和内容治理能力。<p>

**2.1.1用户认证与访问控制**

<p style="text-indent: 2em;">本模块用于完成用户身份核验与登录校验，确保平台用户具备校内学生身份，并为受保护资源访问提供认证基础。<p>
<p style="text-indent: 2em;">用户注册时核验学生身份，登录时使用学号+密码。系统对用户身份进行校验，并生成对应的登录状态与基础用户信息。认证通过后，用户可访问平台受保护资源；认证失败时，系统返回相应提示信息。该功能用于保证平台用户身份真实性，满足校内场景下的使用要求。<p>

**2.1.2. 内容发布功能**

<p style="text-indent: 2em;">本模块用于实现校园内容的提交、校验、审核流转与发布展示。<p>
<p style="text-indent: 2em;">用户可通过发布入口输入文字内容，并按需上传图片等附件，形成完整的发布条目。系统在接收内容后，首先对其进行基础处理，包括必填项检查、内容格式校验、图片上传与存储、数据规范化处理等，以保证发布内容满足平台的基本提交要求。在完成前置校验后，系统将生成对应的待审核内容记录，并自动提交至平台审核流程。对于审核通过的内容，系统将其正式发布并展示在相应页面中，供其他用户浏览、搜索和互动；对于未通过审核的内容，系统将根据审核结果返回相应处理状态，以便用户了解发布结果并进行必要修改，是本项目的核心治理模块之一。<p>

**2.1.3.内容智能审核与风险处置功能**

<p style="text-indent: 2em;">本模块用于对用户发布的帖子与评论进行自动识别、风险分级和审核处置，并通过“AI初审 + 人工复核”机制实现内容审核的效率与准确性提升，是本项目的亮点模块。<p>
<p style="text-indent: 2em;">用户发布帖子或评论后，系统首先对文本及相关内容进行自动识别、风险判定与分级处理。对于规则明确、风险特征清晰的内容，由AI审核模块直接完成初审；对于语义复杂、存在争议或置信度不足的内容，自动转入人工复审流程。系统根据审核结果对内容作出通过、驳回、下架或提交人工复审等处理，并记录相应审核状态与处置结果。该功能通过“AI初审 + 人工复核”的两级审核机制，在保障审核效率的同时提升审核准确性。<p>

**2.1.4. 语义检索功能**

<p style="text-indent: 2em;">本模块用于结合大模型语义理解、内容召回与结果排序，实现面向多样化表达场景的平台内容语义检索。<p>
<p style="text-indent: 2em;">用户输入关键词、短语或不完整描述后，系统依托大模型的语义理解能力，结合检索、召回与排序机制，对平台内相关帖子、话题等内容进行模糊匹配与结果筛选，并输出与用户查询意图较为一致的结果。相较于传统基于字面匹配的关键词检索，该功能能够更好适应用户表达不完整、用词不统一或语义表述多样化的检索场景，从而提升信息发现效率与搜索准确性。该模块同样是本项目的技术亮点模块。<p>

**2.1.5 内容浏览与互动功能**

<p style="text-indent: 2em;">本模块用于实现平台内容的分类展示、标签检索、详情浏览及用户互动反馈。<p>
<p style="text-indent: 2em;">用户可在平台中浏览首页信息流、分类页面、标签页面及内容详情页，系统根据用户请求加载相应帖子内容，并完成分页展示、详情展示及相关信息组织。平台支持按照内容分类和标签进行检索与浏览，便于用户快速定位感兴趣的信息主题，提高内容获取效率。在浏览过程中，用户还可对帖子进行点赞、评论等互动操作，系统同步完成交互状态更新与结果反馈。该功能满足用户在校园场景下进行日常浏览、交流互动和信息传播的需求。<p>

**2.1.6 平台治理与运营管理功能**

<p style="text-indent: 2em;">本模块模块面向平台安全运营与秩序维护，支持对内容、用户行为及举报记录进行统一管理。<p>
<p style="text-indent: 2em;">系统基于角色权限控制实现差异化访问，普通用户具备注册登录、内容发布、互动、搜索、举报及个人信息维护等基础权限；管理员具备内容审核、话题管理、用户治理、举报处置、全局统计查看及审计日志访问等管理权限。针对违规内容，平台支持通过、驳回、下架、恢复等审核操作；针对异常用户，支持警告、禁言、封禁与解封等治理措施；针对举报信息，支持受理、跟踪与处理闭环。该功能通过最小权限原则与访问控制机制，保障平台内容安全、用户秩序与系统稳定运行。<p>

**2.1.7 日志与安全管理系统**

<p style="text-indent: 2em;">本模块用于实现系统运行留痕、安全防护、异常监测、审计追踪及数据备份恢复，保障平台的稳定运行与用户信息安全。<p>
<p style="text-indent: 2em;">本模块将对用户访问、异常报错、关键操作及用户行为等信息进行统一记录与留痕处理，支持后续问题排查、运行监测与安全审计。在安全防护方面，系统应具备权限控制、敏感数据保护及常见前后端攻击防御能力，以降低非法访问和数据泄露风险。针对访问量突增或异常请求等情况，系统应具备基本的监测、限流与恢复能力，保障核心服务的连续性。同时，系统应对删除帖子、封禁账号等敏感管理操作进行审计记录，并支持数据备份与必要的数据恢复，以提升平台运行的安全性、可追溯性和可靠性。<p>

**2.1.8 数据统计功能**

<p style="text-indent: 2em;">数据统计模块用于实现用户行为数据采集、多维指标分析、用户画像支撑及运营决策支持，是平台精细化运营与用户画像构建的基础。<p>
<p style="text-indent: 2em;">本模块能够对用户在平台中的访问、发布、浏览、点赞、评论等关键行为进行持续采集、汇总与分析，形成活跃度、内容传播效果、互动质量和兴趣偏好等多维度数据指标，并进一步支撑用户行为可视化以及运营决策优化，为平台功能迭代与治理策略调整提供数据依据。<p>

### 2.2对功能的一般性规定 
<p style="text-indent: 2em;">本系统各功能模块应遵循统一的界面风格、交互方式和操作逻辑，保证注册登录、内容发布、搜索浏览、互动交流及管理治理等功能在使用体验上的一致性。<p>
<p style="text-indent: 2em;">系统应对用户输入进行统一的合法性、完整性和格式校验，并对成功、失败、待审核、权限不足等状态返回规范、明确的提示信息。<p>
<p style="text-indent: 2em;">所有功能均应基于角色权限控制机制运行，遵循最小权限原则；涉及内容发布、评论、举报等功能的模块应统一纳入“AI初审+人工复核”的审核体系。<p>
<p style="text-indent: 2em;">系统还应具备基本的异常处理、日志记录与帮助提示能力，以保障功能运行的规范性、可追溯性和可维护性。<p>

### 2.3用户界面 
<p style="text-indent: 2em;">根据上述功能定位，本系统的用户界面风格应整体体现校园化、轻量化、清晰化与功能导向性。<p>
<p style="text-indent: 2em;">界面设计应采用简洁直观的布局结构，以信息获取效率和操作便利性为核心，整体风格保持统一、规范，适合学生用户在网页端或移动端进行高频、碎片化使用。<p>
<p style="text-indent: 2em;">首页信息流、分类页、搜索页和详情页应突出内容展示的层次性与可读性，采用清晰的分区设计和一致的导航逻辑，便于用户快速完成浏览、检索和互动操作；发布界面应强调输入流程简明、操作路径短，降低内容发布门槛；智能搜索界面应突出搜索框、结果列表和相关性展示，强化模糊搜索带来的便捷体验；审核与管理界面则应偏向规范、明确和高效，突出状态标识、分类筛选、审核结果反馈及操作留痕，以满足管理与治理需求。<p>
<p style="text-indent: 2em;">总体而言，系统界面风格应兼顾校园社交平台的亲和性与管理系统的规范性，在视觉上简洁统一，在交互上易学易用，在功能呈现上突出搜索与审核两项核心特色。<p>

### 2.4对性能的一般性规定 
**2.4.1 精度**

<p style="text-indent: 2em;">本系统主要处理文本、图片、用户身份信息、审核状态信息、检索结果信息及行为统计数据，不涉及高精度科学计算，因此对数值计算精度无特殊要求。<p>
<p style="text-indent: 2em;">系统应保证用户输入数据、审核结果、检索结果、用户行为记录及统计结果在采集、传输、存储和展示过程中的一致性与完整性，避免因格式转换、传输异常或并发更新导致数据缺失、错乱或状态不一致。对于身份认证、权限控制、审核状态、用户操作记录等关键数据，应保证其记录准确、状态明确、结果可追溯。<p>

**2.4.2 时间特性要求**

<p style="text-indent: 2em;">系统应具备满足校园场景日常使用需求的基础响应性能与稳定运行能力，保障用户交互、内容流转、信息检索及管理治理等核心功能的及时性与可用性。<p>
<p style="text-indent: 2em;">用户注册登录、页面跳转、内容浏览、点赞评论等常规操作应在可接受时间内完成并返回结果；内容发布后应能够及时进入审核流程，审核结果状态应可查询；搜索功能应在合理时间内返回匹配结果，以保证信息获取效率；管理端对审核、下架、禁言等操作应能够及时生效。系统整体应支持普通用户日常浏览、发布、搜索、互动及管理员审核治理等功能的稳定运行。<p>

**2.4.3 灵活性**

<p style="text-indent: 2em;">系统应具备面向校园场景的业务适应性与可扩展性，能够适应终端形态、接口规则及功能需求变化，并支持在保持整体架构稳定的前提下完成配置调整与功能扩展。<p>
<p style="text-indent: 2em;">在操作方式上，应能够适应网页端访问，并具备向移动端使用习惯靠拢的界面与交互设计；在运行环境上，应支持常规校园网络环境下的部署与运行；在接口方面，应具备对身份认证、账号管理及内容审核相关接口变化的适应能力；在功能扩展方面，应支持内容分类、标签体系、搜索策略、审核规则及统计指标的调整与补充；当检索规则、审核标准或管理要求发生变化时，系统应能够在不大幅修改整体架构的前提下进行配置或功能更新。<p>

**2.4.4 输入输出要求**

<p style="text-indent: 2em;">系统应对认证、发布、检索、互动与管理等业务输入输出进行统一规范化处理，确保数据格式完整明确、状态可识别，并满足存储、检索、审核及统计分析等处理需求。<p>
<p style="text-indent: 2em;">本系统输入数据主要包括用户身份认证信息、用户发布内容、搜索请求、互动操作、举报信息及管理操作信息。身份认证输入主要为学号、密码及校园卡或学生证等证明信息；内容发布输入主要为文本、图片及分类标签等信息；搜索输入主要为关键词、短语或不完整描述；互动输入主要包括点赞、评论、收藏、举报等操作请求；管理输入主要包括审核、下架、恢复、禁言、封禁等管理指令。<p>
<p style="text-indent: 2em;">系统输出数据主要包括登录结果、页面展示内容、搜索结果、审核状态、互动反馈、管理处理结果及统计信息。登录输出应明确提示认证成功或失败；内容发布输出应返回待审核、审核通过、审核驳回等状态；搜索输出应返回与查询相关的帖子、话题或分类结果；互动输出应返回操作是否成功及对应状态变化；管理输出应返回处理结果及对应状态更新；统计输出应以汇总数据形式展示活跃度、发布量、互动量等信息。<p>
<p style="text-indent: 2em;">系统输入输出数据应采用统一、规范的格式，保证显示内容完整、语义明确、状态可识别，并满足后续存储、检索、审核与统计处理需求。<p>

**2.4.5 数据管理能力要求**

<p style="text-indent: 2em;">系统应具备对用户、内容、互动、审核、治理及统计等多类业务数据进行分类存储、统一管理与高效查询的能力，并能够适应校内用户规模与业务数据持续增长带来的扩展需求。<p>
<p style="text-indent: 2em;">本系统需管理的数据主要包括用户信息、身份认证信息、帖子内容、图片附件、评论信息、点赞收藏等互动记录、举报记录、审核记录、用户治理记录及统计分析数据。考虑到系统面向校内学生使用，数据规模将随用户数量、帖子数量和互动行为持续增长，因此系统应具备对上述数据进行分类存储、统一管理和按需查询的能力。<p>
<p style="text-indent: 2em;">在系统初期，应能够支持校内用户基础信息、日常发帖数据及互动记录的持续积累，并满足内容检索、审核追踪、行为统计和治理留痕等业务需求。数据管理设计应兼顾当前开发规模与后续增长空间，能够支持用户数量、内容数量及行为数据规模增加后的正常运行与维护。<p>

**2.4.6 故障处理要求**

<p style="text-indent: 2em;">系统应具备对认证、上传、检索、审核、权限及运行环境异常等故障的识别、提示、记录与恢复能力，确保故障状态可感知、关键数据可追溯，并保障核心业务数据的完整性与一致性。<p>
<p style="text-indent: 2em;">系统运行中可能出现的故障主要包括身份认证失败、内容上传失败、搜索结果返回异常、审核流程中断、数据库连接异常、网络中断、服务器响应异常以及用户权限校验失败等。对于上述故障，系统应能够向用户或管理员返回明确、规范的提示信息，避免出现无提示、无响应或状态不明的情况。<p>
<p style="text-indent: 2em;">对于一般性故障，如输入格式错误、登录失败、上传失败、搜索无结果等，系统应允许用户重新提交或重新操作；对于关键性故障，如审核状态异常、数据写入失败、权限控制异常等，系统应记录相关日志，便于后续排查和恢复；对于因服务器、网络或存储异常导致的功能不可用情况，系统应尽可能保证已有数据不丢失、不损坏，并在恢复后维持核心业务数据的一致性与可追溯性。<p>

**2.4.7 其他专门要求**

<p style="text-indent: 2em;">系统应在保障身份数据与关键操作安全可控的基础上，兼顾界面易用、运行稳定、结构清晰及功能可扩展等综合质量要求<p>
<p style="text-indent: 2em;">本系统应满足校园场景下的安全性、可用性和可维护性要求。系统应对用户身份信息、登录信息及管理操作信息进行必要保护，避免未经授权的访问、修改和泄露；涉及身份认证、权限控制、内容审核和治理操作的关键环节应具备明确的访问控制与日志记录机制。<p>
<p style="text-indent: 2em;">在使用方便性方面，系统应保证界面统一、操作简洁、反馈明确，降低普通用户和管理员的使用负担；在可维护性方面，系统应具备较清晰的模块划分，便于后续对搜索、审核、内容管理和统计功能进行维护与扩展；在可靠性方面，系统应保证在常规校园网络环境下稳定运行，并支持基本的异常处理与故障恢复；在可扩展性方面，系统应便于后续增加内容类型、优化审核规则、调整搜索策略及扩展管理功能。<p>

## 3.运行环境规定

### 3.1设备
- 开发与测试阶段拟采用 2 台云服务器或物理服务器，建议配置为 4 核 CPU、8 GB 内存、100 GB 及以上存储空间，用于部署 Web 服务、业务服务、数据库及日志管理模块。
- 如后续访问量增加，可将应用服务、数据库服务与对象存储服务拆分部署。
- 用户侧设备包括可正常访问网页系统的 个人计算机、平板设备和智能手机。
- 管理员侧设备为可访问后台管理页面的 个人计算机，用于内容审核、用户治理与日志审计。
- 数据备份需依赖独立存储空间，用于保存数据库备份文件及必要的日志文件。
  
### 3.2支撑软件（拟采用）  
- 开发环境：Linux
- 编程语⾔：Python（后端），JavaScript（前端）
- 数据库管理系统：MySQL
- 后端框架：Flask
- 前端框架：React（响应式界⾯）
- ⼈⼯智能：通义千问API(模糊搜索和审核)
- 版本控制：Git，Gerrit（代码审查）
- 开发工具：Visual Studio Code

### 3.3接口  

本软件在运行过程中需与前端页面、数据库系统及第三方人工智能服务进行数据交互，并通过统一接口实现模块之间的协同工作。

在前后端通信方面，系统前端采用 React 实现界面交互，后端采用 Flask 提供业务服务接口，二者之间通过 HTTP/HTTPS 协议进行通信，接口风格采用 RESTful API 形式。前后端之间主要使用 JSON 作为数据交换格式，以完成用户认证、内容发布、内容浏览、互动操作、检索请求及审核结果返回等业务数据传输；对于图片等附件上传场景，可采用 multipart/form-data 方式进行文件传输。

在数据存储方面，后端服务通过数据库连接接口与 MySQL 数据库进行交互，主要使用 SQL 语句完成用户信息、帖子内容、评论数据、审核记录、日志信息及统计数据的增删改查操作。Flask 应用与 MySQL 之间通过标准数据库访问协议完成通信，以保证业务数据能够稳定存储和读取。

在智能功能支持方面，系统通过调用 通义千问 API 与外部大模型服务建立接口连接，用于实现语义检索和内容审核功能。该部分通常通过 HTTPS 协议发起远程调用，请求与响应数据一般采用 JSON 格式封装，传输内容包括用户输入文本、检索请求、审核文本、模型返回结果及处理状态等信息。

在开发协作方面，系统代码通过 Git 进行版本管理，并结合 Gerrit 实现代码审查与提交管理。该部分主要服务于开发过程中的代码同步、版本控制和协同维护，不直接参与系统业务运行，但属于软件工程支撑接口的重要组成部分。

综上，本系统对外及对内的主要公共接口包括前后端业务接口、数据库访问接口以及第三方大模型服务接口；主要采用的通信方式包括 HTTP/HTTPS 协议、RESTful 接口规范、JSON 数据交换格式、SQL 数据访问方式，能够满足系统在业务处理、数据存储与智能服务调用等方面的通信需求。

### 3.4控制 
1.用户操作控制：由普通用户通过注册、登录、发布、搜索、浏览、评论、举报等前端操作触发。

2.后台管理控制：由管理员通过审核、下架、恢复、禁言、封禁等后台指令触发。

3.系统自动控制：由系统内部权限校验、审核流转、日志记录、异常检测、数据备份等机制自动完成。

4.控制信号来源：前端请求、管理端操作指令及服务器端业务逻辑规则。
